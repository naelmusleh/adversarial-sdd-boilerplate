# ROLE-CAPABILITIES-001 — Founder-facing orchestrator and optional role capabilities

## Purpose and boundaries

Use this catalog to decide what kind of expertise a task needs. A role is a **capability contract**, not a promise that a dedicated agent or qualified professional is available. The lead agent/orchestrator remains the owner's point of coordination; it reads canonical project records, recommends the next allowed action, and explains material assignments. It does not create another status registry, approve a gate, make owner decisions, or authorize release or external action.

The catalog is repository-native and provider-neutral. Use sequential role-bounded work by default. Use a separate agent only when independent review, distinct expertise, or useful parallel work justifies the handoff and the environment actually provides it. An implementer cannot provide the independent review required by policy. QA evidence and release authorization remain separate outcomes.

## How to use it

1. Start with the approved task, primary persona/outcome, canonical status, requirements, and applicable gate evidence.
2. Match the task to the activation triggers below. Choose the smallest set that can finish the approved work; document a material omission when the owner could otherwise expect it.
3. Carry the exact task/requirement IDs, source revisions, bounded question, expected output, authority limits, and evidence destination into each handoff.
4. If a required capability, tool, or qualified reviewer is unavailable, say so plainly. Keep dependent work blocked or unknown; a substitute capability does not impersonate expertise.
5. Report progress in ordinary language before internal gate IDs. Link each completion claim to current evidence. Ask the owner only for decisions that change scope, cost, risk, promise, or authorization.

For an MVP or large feature, follow the selected ten-working-day target (unless the owner set another date), one primary persona and job, the smallest end-to-end happy path, and concise triggered deferrals. Do not generate exhaustive error matrices, secondary-use-case inventories, extreme edge-case lists, or speculative scale design. Keep the gate-required applicability decisions and safeguards; the MVP label does not waive them.

## Short routing examples

These are workflow examples, not evidence that a particular capability or agent is available.

| Situation | Use | Usually omit | Owner-facing next step |
| --- | --- | --- | --- |
| Routine fix: a small reproducible bug | Implementation capability; required reviewer/QA under app policy. Add debugger only if routine diagnosis fails. | Research, growth, legal, platform roles without a concrete trigger. | “I’ll fix the reported behavior and run the checks linked to this task. I’ll ask you only if scope or expected behavior is unclear.” |
| Focused MVP feature | Orchestrator, product design if user journey changes, selected platform implementer, required independent review and QA. | Growth, social media, dashboard, optimizer, secondary platform roles unless approved objective/risk triggers them. | “We’ll deliver the smallest path for the primary user by the target date. I’ll keep required safeguards and show only material scope/date trade-offs.” |
| Market bet before build | Research, feasibility, and growth capabilities for a bounded experiment; owner decides whether to build/spend. | Build team until the decision to commit is made; publication without authorization. | “I’ll test the highest-risk market assumption and bring you the evidence, limits, cost, and build/no-build options.” |
| Post-launch improvement | Operator/reporting plus the one capability tied to observed evidence (growth, communications, debugger, or optimizer). | Unrelated specialists and continuous optimization without a goal. | “I’ll use the observed issue or outcome to propose one bounded improvement; external action still needs the recorded approval.” |

## Role-record and compatibility rules

- `role_id` MUST be stable and unique and match `ROLE-[A-Z0-9-]+`.
- `classification` MUST be one of `existing-role`, `on-demand-specialist`, `operational-responsibility`, `product-capability`, `excluded`.
- `execution_mode` MUST be one of `sequential-role-mode`, `separate-agent-justified`, `qualified-external-review`, `operational-procedure`, `not-applicable`.
- Every field in the table is required and non-empty. `artifact_refs` uses semicolon-separated existing canonical artifact IDs.
- Adding optional explanatory text is a minor catalog-version change. Changing required fields, enum meaning, authority, or role identity is a major change and needs review. A validator that does not support the schema's major version must fail closed.
- The structural checker verifies table shape, unique IDs, field presence, enums, and artifact references only. It cannot judge whether a trigger is wise, expertise is qualified, a role should be activated, or a gate passed.

Per-app availability and activation may be recorded in that app's own approved artifacts. Do not copy or edit this framework catalog as a competing status source.

## Evidence boundary

The source roster is a comparison input, not proof that the roles improve productivity or are implemented as separate agents here. This catalog specifies process and handoff behavior only. It does not promise legal/security expertise, runtime dispatch, measured cycle-time gains, autonomous external actions, or Infinite Gallery role activation.
