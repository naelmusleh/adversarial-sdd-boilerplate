# FRAMEWORK-FEASIBILITY-010 — FW-TASK-029 signed evidence receipt feasibility

## Scope and exclusions

This is a bounded G-FEAS plan for FR-FW-032–034 under DECISION-027. It will assess whether a compact receipt can bind exact repository/source identity, the required-check manifest, trusted workflow identity, hosted check results and evidence digests; whether a standalone verifier can validate the signed receipt with locally supplied trust material; and what issuer, key rotation, replay, privacy and claim limits remain.

The plan does not select or adopt a provider, signer, key-management mechanism, receipt format, or application integration. It does not change repository CI policy, use production credentials or product data, replace FW-TASK-020's app-hosted CI requirement, alter FW-TASK-028, or authorize implementation. Any hosted probe uses synthetic content, a temporary `workflow_dispatch` workflow, an ephemeral hosted runner, no repository secrets, and the minimum temporary permissions needed for the tested operation. The temporary workflow and generated data are removed after evidence capture. No claim about branch protection or trusted-branch enforcement is made.

## Dated primary-source observations

Official GitHub documentation describes artifact attestations as signed claims that can include repository, organization, environment, commit SHA, triggering event, and workflow information. GitHub's `actions/attest` supports a custom predicate and requires `id-token: write`, `attestations: write`, and `artifact-metadata: write`; this permission surface must be isolated and justified. GitHub documentation recommends attestations for released artifacts and warns that an attestation does not guarantee an artifact is secure. It discourages signing individual source/document files or frequent test builds; a one-per-run governance receipt is not explicitly evaluated as a supported subject pattern, so the probe must treat fit as an open question. Sources: [GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations), [actions/attest](https://github.com/actions/attest), and [GitHub attestation setup](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).

GitHub documents offline verification using the receipt/artifact bytes, a downloaded attestation bundle, and trusted-root material. The `gh attestation verify` interface supports repository and signer-workflow identity constraints, a custom trusted root, and JSON output for additional policy checks. For offline bundles, repository name alone cannot detect a rename or name reuse; the signing certificate's repository ID must also be compared with a separately trusted expected ID. GitHub's public repositories use Sigstore Public Good; private repositories use GitHub's Sigstore instance, which has no transparency log and only federates with GitHub Actions. The offline guide warns that previously exported root material can become stale after key rotation and cannot reveal later revocation. Sources: [offline verification](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline), [gh attestation verify](https://cli.github.com/manual/gh_attestation_verify), and [gh attestation trusted-root](https://cli.github.com/manual/gh_attestation_trusted-root).

Sigstore Cosign also supports keyless blob signing with a bundle containing the signature, certificate, and transparency-log inclusion proof, with issuer and signer identity checks. Its suitability for the repository's required workflow identity, private-repository trust path, receipt predicate, and offline policy remains to be compared rather than assumed. Source: [Sigstore Cosign verification](https://docs.sigstore.dev/cosign/verifying/verify/) and [blob signing](https://docs.sigstore.dev/cosign/signing/signing_with_blobs/).

2. Pin every external action by immutable commit SHA. ## Frozen synthetic check policy and temporary workflow design

The expected policy fixture is schema `sdd-required-checks/v1`, with profile `governance-receipt-probe`, source ref `refs/heads/codex/v2-backlog-roadmap`, workflow path `.github/workflows/verify-pipeline.yml`, workflow definition ref equal to the exact source ref, gate contract `FRAMEWORK-GATE-CONTRACT-001` version `1.2` at the exact source revision and its SHA-256 digest, expected check app slug `github-actions`, and immutable GitHub Actions app ID `15368`. It contains exactly these three required check names, as shown in the repository's observed branch-rule configuration: `Metadata & Artifact Audit`, `Initializer Regression Gate`, and `TypeScript Static Code Analysis`. For the positive case, the temporary workflow resolves exactly one completed successful Verify Pipeline workflow run for the exact triggering source SHA, ref, event, and workflow path; it records that run ID, attempt, workflow identity, head SHA, and event. GitHub's workflow-runs API supplies the workflow `path` and `head_branch` as separate fields; the probe requires the exact path and derives the ref from `refs/heads/{head_branch}`, then checks it against the expected ref. It does not assume the API's `path` field embeds a ref. The probe then queries the GitHub Checks API and accepts each required check only if its check-suite/run identity and attempt correspond to that one resolved workflow run, its `app.id` is `15368` and slug is `github-actions`, and its name, conclusion, and head SHA match the frozen policy and source SHA. Every check in the receipt therefore shares the same repository ID, run ID, attempt, workflow identity, event, ref, and source SHA. Missing or multiple candidate runs, a retry ambiguity, missing/duplicate/pending/unexpected checks, or any mismatched run/app/workflow/ref/event/SHA fails closed. Repository ID comes from GitHub repository metadata and is recorded as observed evidence. The required-check manifest SHA-256 is computed over canonical UTF-8 JSON (sorted keys, compact separators, no trailing newline). Negative fixtures mutate one observed field at a time, including omitted/duplicate check, changed name or ID, wrong app ID, run ID or attempt, gate-contract version/revision/digest, workflow identity/ref, event, ref, non-success conclusion, wrong head SHA, wrong manifest digest, and wrong repository ID. Negative-case values are synthetic and are never used as positive provider evidence. This probe does not re-establish branch protection; it uses the already observed check names as policy input.

The temporary reusable workflow is `.github/workflows/fw029-evidence-probe.yml`, called only by the already-present Verify Pipeline `workflow_dispatch` run when its ref is exactly `refs/heads/codex/v2-backlog-roadmap`. GitHub requires a `workflow_dispatch` workflow to exist on the default branch, so this temporary workflow itself uses `workflow_call`; it is not directly dispatchable. The reusable workflow independently checks the provider-supplied `github.workflow_ref` equals the exact repository, Verify Pipeline workflow path, and authorized ref, so another workflow cannot call it and obtain a receipt. The caller job grants its maximum required permissions, while the reusable workflow narrows them per job: the preparation job gets only contents/actions/checks read, and the signing job gets artifact-read plus OIDC/attestation write permissions. The run is not available on push or pull request events, and no secrets are used. A read-only preparation job checks out the exact triggering SHA using the pinned checkout action, asserts the Verify Pipeline workflow definition ref equals the authorized ref, reads the exact gate contract and rejects any version other than `1.2`, resolves one exact successful Verify Pipeline run and attempt for that same SHA/ref/event/workflow path, queries actual check-run records, joins required checks only when their check-suite identity belongs to that run, validates app ID `15368`, obtains repository ID from GitHub metadata, builds the receipt from those observed values, and computes receipt/evidence digests. On the source `push` run, the workflow also exposes one known optional caller job, `FW-029 Synthetic Evidence Probe`; the probe requires it to appear exactly once with conclusion `skipped`, excludes it from the receipt, and rejects any other unexpected job. It fails closed on missing or ambiguous runs, attempts, or checks, and any app/workflow/ref/event/SHA/contract/caller-identity mismatch. A separate signing job downloads only the bounded receipt artifact, invokes the pinned attest action, downloads the resulting attestation bundle with `gh attestation download`, and uploads only the receipt and bounded bundle for one-day retention. No repository code is executed beyond the checked-in workflow steps, and no untrusted PR payload is accepted. Offline verification is a separate local step using explicit receipt, bundle, trust root, and policy files; it must verify the issuer/workflow identity and then enforce all observed provider and gate-contract fields plus the synthetic mutation cases, including rejection of altered or stale contract digests. The exact caller and reusable workflow files, rendered permissions, and action pins must be independently reviewed before execution; any deviation requires a new plan revision and review.

## G-FEAS pass boundary

G-FEAS may pass only if at least one candidate can produce and independently verify a receipt bound to the exact source, required-check manifest, trusted workflow identity, provider check evidence and artifact digests; negative substitution/tamper cases fail; and privacy/permission limits are bounded. If no candidate meets those conditions, record the blocker and stop. A pass establishes feasibility only for the observed repository visibility, GitHub-hosted runner, candidate pins and trust-root snapshot. It does not choose a provider/key strategy, establish root freshness or revocation, prove repository branch protection, prove test adequacy or authorize production adoption.

## Independent review and corrected verification matrix (2026-10-24)
