# FRAMEWORK-FEASIBILITY-008 — FW-TASK-013 feasibility screen

## Scope and exclusions

This is a bounded G-FEAS screen for FR-FW-025–027: a runtime-neutral governance core, explicit Next.js/TypeScript, FastAPI/Python, and Rust/Axum framework profiles, and cross-module contracts. It establishes what can be verified next in this local template checkout. It does not claim profile support, select Infinite Gallery technology or providers, authorize app implementation, migrate applications, split repositories, or introduce native Gallery requirements. The accepted sample is framework fixture input only.

## Dated observations

On 2026-10-23, local inspection observed Python 3.13.2, Node.js v22.23.3, and npm 12.1.0. `uv`, `rustc`, and `cargo` were not on PATH; FastAPI was not installed. The repository Verify Pipeline configures Python 3.13 and Node.js 22 but does not configure Rust or run a Next.js application build. Its pass proves the existing Python suites, artifact validation, TypeScript compiler, Vitest suite, configured coverage, and app initializer regression only. It does not prove profile isolation or app-stack support.

Official documentation supports the following as **candidate experiment pins only**: the repository already locks Next.js 15.5.27 and TypeScript 5.9.3; [Next.js installation docs](https://nextjs.org/docs/app/getting-started/installation) give Node.js 20.9 as a minimum. The [FastAPI tutorial](https://fastapi.tiangolo.com/tutorial/first-steps/) states Python 3.10+ and the [official FastAPI release page](https://github.com/fastapi/fastapi/releases) lists FastAPI 0.157.0 as latest on 2026-10-23. The [official Rust book](https://doc.rust-lang.org/stable/book/title-page.html) currently assumes Rust 1.97.0 with edition 2024; [docs.rs Axum](https://docs.rs/crate/axum/latest) lists Axum 0.8.9. [PyPI pytest](https://pypi.org/project/pytest/) lists 9.1.1 and [PyPI HTTPX](https://pypi.org/project/httpx/0.28.1/) documents stable 0.28.1. [PyPI pip 26.2.2](https://pypi.org/project/pip/26.2.2/) provides the pinned resolver, [Vitest 5](https://main.vitest.dev/blog/vitest-5) requires Node.js 22.12 or later, [Serde releases](https://github.com/serde-rs/serde/releases) include 1.0.228, and [serde_json 1.0.145](https://docs.rs/crate/serde_json/1.0.145) is documented. Sources checked 2026-10-23. These pins are probe inputs only, not an Infinite Gallery decision, permanent framework support policy, or proof of mutual compatibility.

## Applicability screening

This G-FEAS scope is a framework-only, non-production exercise over synthetic metadata. Product data/provider rights, user identity, customer privacy, application-region availability, product workload performance, production service cost, support/on-call ownership, and stored-data recovery are not applicable to these probes: no product data, provider integration, deployed service, persistent store, or production workload is used or promised. The applicable platform/toolchain questions are covered by FEAS-FW013-01 through -03. Security exposure is limited but not absent: the hosted runner downloads pinned setup actions and packages from external registries with runner egress; the jobs contain no user secrets or private product data, disable persisted checkout credentials, use read-only repository permission, and are destroyed after execution. This residual is a condition of the evidence, not a claim of sandboxed egress. Owner/status: framework owner; screened for this bounded scope on 2026-10-23; reopen if the experiment adds product data, external services, persistence, or production workload.

## Bounded non-production experiment plan and execution

The plan runs only on a disposable GitHub-hosted `ubuntu-24.04` VM, with no user secrets, no write-capable token, no OIDC permission, checkout credentials disabled, and no user-home or host-data mounts. The job grants `contents: read`; checkout uses `persist-credentials: false`; the token is not passed to package/build commands; no artifact-upload action or deployment step is used. Setup actions use the pinned revisions already present in Verify Pipeline; the exact runner image and commit are recorded. It handles synthetic metadata only. Registry restore/build tools execute third-party code with unrestricted runner egress during provisioning; this residual exposure is recorded and limited by absence of secrets/private data and destruction of the VM after the run. A local `/tmp` directory alone is expressly not an execution boundary. No dependency is added to the framework's root package or runtime.

## Plan acceptance criteria

The cross-profile probe compares interface outcomes only; it does not implement or prove persistence, list/removal lifecycle behavior, authorization, storage, upload, or production runtime semantics.

The experiment plan is adequate only if all four probes have clean-target setup, exact direct inputs, revision-bound fixture source, retained resolved lockfiles, observable outputs, and explicit failure classification; synthetic sample use is traceable to the accepted digest; execution uses an ephemeral hosted VM with no user secrets or host data mounts, and does not pass the read-only repository token to package/build subprocesses; skipped profiles remain non-passing. Registry/build-tool egress during restore is an explicit residual exposure. Cross-contract comparison must use the six named fixtures and commands listed above. Profile composition/leakage remains unavailable before a composer exists, and is not represented as feasibility evidence. An independent reviewer must check this exact plan and generator before execution. G-FEAS may pass only after run evidence and dependency-state reconciliation exist and independent review endorses the bounded disposition.
