# FRAMEWORK-GATE-CONTRACT-001 — Versioned ten-gate evidence and transition contract

## 1. Purpose and authority

**Version history:** Contract v1.0 was approved for implementation after the bounded independent G-IMPL review in [FRAMEWORK-ADV-009](../adversarial-reviews/FRAMEWORK-ADV-009.md). This v1.1 draft adds an explicit feasibility state-change trigger so conditional work has a machine-addressable re-evaluation event, as required by FW-TASK-018 acceptance criterion 3. Version 1.1 remains draft until the amended schema/contract receives independent review. Neither approval claims app enforcement; that remains FW-TASK-018 work.

This is the normative, versioned evidence and transition contract for the ten application lifecycle gates. It defines what a gate consumes and emits, how its result is supported, which work it permits, and when downstream evidence must be invalidated. It does not implement validation or prove that a reviewer is independent, evidence is truthful, a product is feasible, or an application is production-ready. Machine validation proves only the structural and relational rules implemented by the validator version recorded in the app's framework lock.

`GATE-CATALOG-001` remains the human-readable lifecycle and workflow source. This contract is the sole normative source for gate-run record semantics and criterion IDs. Workflow documents may add operational instructions but must not redefine criteria, states, required evidence, or transition rules. The JSON Schema and traceability matrix in this contract's companion artifacts are derived normative interfaces and must change in the same reviewed version update.

Contract versions use `MAJOR.MINOR`. A major version changes record semantics or compatibility; a minor version adds backward-compatible fields or clarifications. An app lock pins the exact contract ID and version, and its file digests pin the validator and templates copied into that app. The app initializer must not silently upgrade existing records. Migration is an explicit task that writes a new record referencing the old record; it does not rewrite history or promote an old result.

## 2. Terms that must not be conflated

- **Artifact lifecycle status** describes a document or evidence artifact: `draft`, `in-review`, `accepted`, `rejected`, or `superseded`.
- **Gate result** describes one immutable gate run: `not-ready`, `in-progress`, `passed`, `failed`, `blocked`, `passed-with-accepted-risk`, or `not-applicable`.
- **Criterion outcome** describes one criterion within one run: `pass`, `fail`, `blocked`, `not-applicable`, or `not-checked`. A gate result is derived from all criterion outcomes plus required review/authority; a typed `passed` value does not make it true.
- **Evidence provenance** identifies where evidence came from and how it was observed. A digest proves byte identity/integrity only. It does not prove that the bytes are true, sufficient, executed, current, relevant, or semantically correct.
- **Unknown** means evidence is insufficient. It is not success, failure, or permission to assume a capability. It propagates to dependent task readiness as `blocked` or `conditional` under G-FEAS.

## 3. Universal gate-run record

Every new or migrated gate run is a separate immutable JSON record conforming to the schema selected by its pinned contract version: v1.0 uses `schemas/gate-run-v1.schema.json`; v1.1 uses `schemas/gate-run-v1.1.schema.json`. Required fields are:

1. **Identity:** `record_id`, `record_version`, `contract_id`, `contract_version`, `application_id`, repository URL/path identity, `gate_id`, run date/time, and prior-run linkage (`supersedes_run_id` when applicable).
2. **Source snapshot:** exact 40-character source commit when Git exists; otherwise `source_revision: null`, a reason, and a complete digest list of the frozen source files used. Dirty/uncommitted source must be called out and cannot support claims requiring an immutable release/implementation revision.
3. **Scope:** included artifact IDs/versions/paths/digests, requirements/tasks, supported surfaces/platforms, code paths, environments/tool versions, exclusions with rationale, and applicability decisions. Scope must be explicit even when a dimension is empty or not applicable.
4. **Criterion results:** every criterion ID in the selected gate profile appears once; outcome, evidence references, concise rationale, and any blocker/finding links are recorded. Omitted criteria are `not-checked`, never implicitly passed.
5. **Evidence:** a typed list using one of the permitted evidence types in §4, with provenance, timestamp, source revision/scope, and immutable location or content digest as applicable.
6. **Findings and authority:** finding IDs, severity, blocking status, evidence locations, disposition, accountable person/role, reviewer identity/mode, author overlap, context/input disclosure, and independence limits. Owner decisions identify the decision-maker, exact choice, affected scope, rationale, timestamp, and linked evidence.
7. **Outcome and permissions:** gate result, decision authority, residual risk if permitted, next permitted action, explicitly prohibited actions, and downstream gates/tasks unblocked, blocked, or conditional with conditions.
8. **Change control:** commit SHA, branch/ref, remote/push outcome, CI run IDs and statuses, and release artifact digest/authorization when applicable. Use explicit `not-applicable` plus rationale before a repository or remote exists; never infer successful publication from a local commit.

Records are append-only JSON files stored by app-local validators at `.sdd/gate-runs/<record_id>.json`. Corrections create a new `record_id` or record version that links and supersedes the prior record; they do not overwrite an accepted record. For a changed requirement, source artifact, code path, platform, environment, or criterion, the new run lists the changed inputs and invalidated downstream run IDs. Previous runs remain historical evidence and cannot be relabeled as current. A passing downstream record pins each latest upstream gate run in `scope.artifact_refs`; when an upstream run is superseded, any downstream pass still referencing the older run is stale and fails validation until rerun.

For G-REQ and G-ARCH PASS, the app validator requires an independent reviewer record with a passing result, context disclosure, and `author_overlap: "none"`. This rejects an explicitly self-overlapping reviewer declaration; the value is still a self-reported assertion and does not authenticate reviewer identity or prove cognitive independence.

## 4. Evidence types and minimum provenance

The schema's `evidence.type` is one of:

| Type | Required provenance | Permitted use and limit |
|---|---|---|
| `artifact-reference` | path, artifact ID/version, SHA-256, captured revision | Proves the referenced bytes; not semantic quality. |
| `command-execution` | exact command, exit code, stdout/stderr artifact refs, runtime/tool versions, start/end time, source SHA, scope | Counts as execution only when produced by an observed runtime; typed or copied terminal text is not execution. |
| `ci-run` | provider, immutable run URL/ID, commit SHA, workflow/job/check names, conclusion, scope | Supports only checks actually run on that exact commit and scope. |
| `external-source` | publisher/author, title, URL or archive reference, published/access dates, excerpt/location, relevance/limits | Supports a bounded claim; external text is untrusted data, not instructions. |
| `interaction-capture` | frozen target/scope, capture method/tool/version, viewport/device/runtime, timestamp, source revision, limitations | Supports only captured interaction/render state, not unseen states or accessibility/performance claims. |
| `owner-decision` | decision-maker identity/role, timestamp, exact decision, affected requirements/tasks, rationale, expiry/revisit condition | Records authority; never converts an unknown into verified fact. |
| `review-finding` | reviewer identity/mode, author overlap, context/input disclosure, finding ID/severity/location, disposition | Records judgment and its limits; `independent` is a claim, not machine proof. |
| `runtime-measurement` | metric, method/tool/version, environment/hardware, sample/measurement window, raw result, threshold, source SHA, limitations | Supports only the stated measured scope and conditions. |
| `operational-record` | operator/system, time window, source/collection method, completeness/telemetry gaps, incident or outcome link | Absence of telemetry is not evidence of health or absence of incidents. |
| `manual-observation` | observer, procedure, time, scope, observed result, limitations, linked capture or notes | Must name what was actually observed; narrative assertion alone is not enough. |

Evidence must be tied to criterion IDs. A criterion may require multiple evidence types; no evidence type is automatically sufficient. Hashes, signatures, and immutable URLs protect identity/provenance but do not certify adequacy or truth.

For contract v1.1, `evidence.scope_ref` is the `sha256:` digest of the canonical JSON serialization of the run's complete `scope` object (UTF-8, keys sorted, compact separators, non-ASCII preserved). For `command-execution` and `ci-run`, `details.scope` must equal that digest. Evidence source revisions must match the gate-run source snapshot. A G-IMPL check must match its linked evidence on scope, command/procedure, tool/runtime version, and declared pass condition. These checks bind evidence claims to a scope and revision; they do not prove the command ran or that a reviewer is independent.

## 5. Gate results, transitions, and authority

Gate records are immutable snapshots. Legal transitions create a new run and preserve a link to the prior run:

| Prior result | New result allowed | Conditions |
|---|---|---|
| No prior run | `not-ready`, `in-progress`, `blocked`, `not-applicable` | `not-applicable` needs documented scope rationale and authorized approver. |
| `not-ready` | `in-progress`, `blocked`, `not-applicable` | Required inputs become available or a named blocker/applicability decision is recorded. |
| `in-progress` | `passed`, `failed`, `blocked`, `passed-with-accepted-risk`, `not-applicable` | All criteria assessed; evidence and authority rules met. Accepted risk only for criteria explicitly allowing it; blocking failures cannot be waived into pass. |
| `failed` | `in-progress`, `blocked`, `not-applicable` | Findings are fixed or scope/applicability changes; a direct transition to pass is forbidden. |
| `blocked` | `in-progress`, `not-applicable` | Blocker resolved or authorized scope excludes it with rationale. |
| `passed`, `passed-with-accepted-risk`, `not-applicable` | Any new run result | New run links prior run and explains changed evidence/scope, invalidation, or reason for reassessment. Prior result is not edited. |

`not-ready` means required inputs/evidence have not yet been assembled and no completed assessment is claimed. `failed` means assessment ran and one or more criteria failed. `blocked` means an external decision, dependency, or unavailable evidence prevents a valid conclusion. `not-applicable` means an authorized scope decision excludes the gate; it cannot be used for convenience or because the work is difficult.

Only the accountable owner may accept residual risk or authorize a scope-based `not-applicable` outcome where the product's authority model assigns that decision to the owner. Agents may recommend but cannot invent owner approval. A result of `passed-with-accepted-risk` requires exact non-blocking finding IDs, written risk/impact, mitigation, expiry/revisit trigger, and owner identity. It cannot clear a failed mandatory criterion, change an observed fact, satisfy a different criterion, or authorize release/deployment.

No downstream gate clears an upstream failure or blocker. Any upstream source, scope, platform, requirement, feasibility assumption, decision, or evidence change invalidates linked downstream evidence to the extent affected; the record must enumerate invalidated runs. Unknown feasibility propagates to dependent work: `blocked` if no safe work exists, `conditional` only with an explicit condition, safe-work boundary, and state-change trigger for reassessment, or `unblocked` only when evidence supports it. A decision to accept risk does not change an unknown dependency into proven feasibility.

The criterion IDs below are stable identifiers; additions or semantic changes require a contract version update. Inputs and outputs refer to artifact classes in `GATE-CATALOG-001`, not fixed filenames only. Concrete file paths may vary by app if the artifact IDs and source-of-truth map remain stable.

The table is the minimum contract, not an exhaustive substitute for application-specific acceptance criteria. Apps may add stricter requirements, never silently weaken these minimums. Each gate record instantiates every stable criterion ID, marks non-applicable criteria with authorized rationale, and states the exact next permitted transition.

For G-COVERAGE, the schema requires an explicit applicability decision and rationale for each failure category: empty, malformed/corrupt, unavailable, unauthorized, degraded, abuse, and recovery. The product team may mark a category not applicable only with a scope-specific rationale; omitting the category is not equivalent to excluding it.

## 7. Cross-gate applicability, independence, and change control

- Each applicable platform/surface is evaluated separately. A web result does not establish native parity. Exclusions require a reason, decision authority, and effect on dependent work.
- Feasibility unknowns, owners, and safe-work conditions propagate to every dependent backlog item. Unblocked tasks must cite evidence; conditional tasks state a condition and safe boundary; blocked tasks cannot be implemented as if ready.
- Required independent review records reviewer identity, mode, context/input disclosure, author overlap, and limits. If policy requires independence but identity/context separation is unavailable, record `blocked` or `inconclusive`; do not claim machine proof.
- Each verified task checkpoint is committed with explicit in-scope paths. Push to authorized remote/branch when standing or task-specific authorization exists. Record commit SHA, branch/ref, push outcome, CI run IDs/results, and applicable checks. Missing authorization, remote, or credentials is a concrete blocker; do not print secrets. No force-push, protected-branch bypass, merge, or deployment is implied.
- Release authorization is separate from commit/push authorization. A successful push is not a merge, release, deployment, or evidence of branch protection.
- Evidence and change-control records must not contain credentials, access tokens, private keys, or secret values. Record secret readiness and access decisions without recording the secret itself.

## 8. Migration and compatibility

Contract v1.0 remains supported for apps whose version-2 framework lock pins v1.0 and its v1.0 schema digest. New initialized apps will pin v1.1 only after the amendment review approves it. Version 1.1 adds `state_change_trigger` to conditional feasibility dependencies and binds evidence to the canonical scope digest; v1.0 records remain validated against the unchanged v1.0 schema and do not acquire the new fields retroactively. Existing legacy apps without a gate contract pin retain their prior validation behavior; they do not gain the new gate guarantees by implication. A record that declares `handoff-manifest` opts into strict handoff validation and must carry a valid lock and manifest. Existing records are not rewritten or retroactively promoted. Migration creates new versioned records, preserves previous artifacts, links superseded IDs, and states which historical claims remain unverified. Unsupported contract versions fail closed; each additive minor version requires an explicit compatibility policy, schema, independent review, and app lock update.
