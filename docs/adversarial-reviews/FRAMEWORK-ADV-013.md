## Findings and dispositions

1. **G-COVERAGE allowed platform substitution.** The first disposable-app pilot accepted scope `ios` with applicability `android`. The validator now requires exact scope-to-applicability reconciliation and rejects missing, out-of-scope, or duplicate platform rows. Fix: `ee47a13792888c213b3848dc22290a7d10bad68b`; hosted checks passed, and the fresh pilot pinned to the later framework revision rejects the same substitution.
2. **G-INTENT accepted fabricated manual evidence.** The second pilot accepted a PASS supported only by a synthetic manual observation with a non-file locator and hash-shaped value. The validator now requires a current `mission.md` artifact-reference and exact-digest accountable-owner approval linked from every criterion. Fix: `927fbdeee820d72ce5c008d2f81f88c02346239f`; positive, forged, and mismatched paths are covered by framework tests, and the separate-app harness confirms the positive/forged boundary.
3. **Pilot initially lacked durable isolated-app regression coverage.** The result depended on temporary scripts and ephemeral app state. A committed harness now creates and validates a fresh disposable app in the framework test suite. It preserves no temporary app as a product artifact and makes the tested operations reproducible from the test suite.
4. **Explicit self-review overlap was not rejected.** An independent reviewer found that G-REQ/G-ARCH only required a reviewer marked `independent` with disclosure; an explicit `author_overlap: "same-agent"` was ignored. The validator now requires `author_overlap: "none"`, and the pilot asserts that explicit same-agent overlap is rejected. This is a declared field only; a dishonest reviewer can still misstate it, and identity remains unauthenticated.
5. **The initial harness overclaimed negative coverage.** The independent reviewer found that invalid-fixture cases removed upstream records and accepted any nonzero result, so failures could come from missing dependencies. The harness now preserves the ten baseline gate records, upgrades fixture identities/revisions/scope bindings to v1.2, removes one gate-specific required field per fixture, and asserts the exact missing-property diagnostic. Selected false-PASS/evidence attacks also assert targeted diagnostics. This closes the vacuity of those ten schema-negative fixtures but does not complete the broader bypass matrix or establish semantic adequacy.
6. **Named gate bypasses exposed incomplete PASS guards.** The pilot now rejects G-INTENT PASS without mission-linked exclusions, G-COVERAGE PASS with only non-applicable failure modes, G-ARCH PASS with no linked verification or only narrative observation, and G-OPERATE PASS without a telemetry-gap declaration or degradation bounds. It also asserts the intended G-RELEASE digest/authorization diagnostics and rejects manual-observation or non-passing G-IMPL check evidence. These are structural controls added in `e9c877c` and tested in `6619d30`/`c3ed401`; they do not establish semantic completeness or authenticate the people and runtimes that supplied evidence.
7. **Structured command evidence is forgeable.** The latest harness writes copied terminal text to a durable file, gives it a content hash, types the evidence as `command-execution`, and links it to a passing check claim. The app validator accepts that evidence record while the gate remains `in-progress`; the test does not claim a G-IMPL PASS. This proves that evidence typing, paths, and hashes do not establish execution provenance. A trusted-runner/attestation policy was selected in DECISION-019 and implemented for lock-v4; its real provider path remains unobserved in an app-hosted run.
8. **The app lock could substitute the attester trust root.** Independent review found that the validator derived the signer repository from mutable app lock data, while the initializer allowed a custom framework URL. Commits `90ad507` and `d9c135b` close alternate-repository substitution for lock-v4: the initializer rejects noncanonical framework URLs; the trusted-CI schema fixes the signer workflow to `naelmusleh/adversarial-sdd-boilerplate/.github/workflows/sdd-trusted-ci-attest.yml`; and the app validator independently requires that canonical framework URL and signer. A regression test rejects an attacker repository in lock/policy data. Independent reviewer `/root/review_fw018_final` confirmed this specific bypass is closed. The remaining boundary is that the app lock chooses the immutable revision within the canonical repository; it does not constitute an externally signed allowlist of approved framework revisions. Forks require separate, reviewed trust-root enrollment.
9. **Invalid-fixture failures could be vacuous under v1.2.** The ten legacy invalid fixtures omitted the required `gate_result`, so upgrading them to contract v1.2 could reject every case before exercising its supposed gate condition. Commit `d9c135b` sets the v1.2 version and in-progress result, refreshes source/scope bindings, removes one gate-specific required field per fixture, and asserts the exact missing-property diagnostic under the correct gate label. This establishes ten targeted schema-negative cases; it does not substitute for the broader adversarial bypass matrix or prove semantic gate adequacy.

## Limits and claims not established

- **Structural versus semantic:** The validator checks schema, IDs, references, source/digest relationships, transitions, scope relationships, and required evidence classes. A matching hash proves byte identity only; it does not prove that mission, feasibility, tenant isolation, test output, prototype critique, operations evidence, or user outcome is truthful or adequate.
- **Evidence provenance:** Repository-controlled CI can lie, tests can be malicious or shallow, and a local runner is not an immutable execution attestation. The harness demonstrates that specific forged or missing structures are rejected; it does not make all evidence truthful.
- **Attestation control not exercised end to end:** Lock-v4 G-IMPL PASS now requires `gh attestation verify` against the canonical trusted workflow identity, immutable signer digest, source SHA/ref, report digest, and check manifest; local or typed command evidence alone cannot pass. Unit tests exercise verifier argument construction and fail-closed paths, but the provider-verification call is stubbed in tests and no separate app has produced a real hosted attestation. Thus the copied-output bypass is blocked by the implemented acceptance rule in local validator tests, while end-to-end provider provenance remains unobserved.
- **Independent review:** Review mode and reviewer metadata are procedural claims. The schema cannot authenticate identity, prove cognitive independence, or prevent collusion.
- **Platform / interaction:** No real UI exists in this Python-engine scenario. G-CX correctly remains unverified/in-progress; no visual quality, accessibility, cross-platform parity, or user research claim is made.
- **Remote / hosted app CI:** The disposable app intentionally has no remote and its generated app workflow was not run on a hosting provider. Push/CI outage and authorization behavior are only locally modeled. The framework repository hosted CI result is not the app's CI result.
- **Release / operation:** No artifact was released, no deployment occurred, and no backup/restore, tenant isolation runtime test, long-duration JSON growth, telemetry loss, or incident drill was run. No production-readiness claim is supported.
- **Repository controls:** Branch-protection settings remain unverified (the prior settings query returned HTTP 403); successful workflow runs do not establish merge protection.
- **Positive PASS applicability:** Only G-INTENT and G-SETUP have synthetic positive PASS paths. The other gates remain in-progress because this disposable app has no owner-approved product requirements/review (G-REQ), empirical feasibility evidence (G-FEAS), approved journeys/platform scope (G-COVERAGE), designed data/security contracts (G-ARCH), selected product implementation task/checks (G-IMPL), release artifact/environment/authorization (G-RELEASE), or deployed users/outcomes/telemetry (G-OPERATE). Passing these gates would fabricate product state. G-FEAS route tests exercise accepted in-progress dependency-state shapes, not feasibility PASS.
- **G-CX criterion 6 disposition:** Not applicable to a positive interaction/PASS fixture in this validator-only, no-product pilot. The app has no evaluator/API/CLI product behavior or rendered interface to observe; fabricated interaction evidence would be false. The negative path records the absence as an explicit limitation and keeps G-CX `in-progress`; this does not exempt an actual application from product-appropriate interaction evidence.

After owner decision DECISION-019 and implementation, reviewer `/root/review_fw018_final` confirmed the alternate-repository trust-root bypass is closed but returned **BLOCK** on FW-TASK-020 completion because app-hosted attestation and broader acceptance-matrix evidence remain outstanding. ## Pilot disposition

**Provisional: structural controls improved; completion evidence remains insufficient.** The validator now requires trusted provider attestation for lock-v4 G-IMPL PASS, rejects alternate-repository signer substitution, and rejects the copied-output fixture as a passing G-IMPL claim. The pilot has G-INTENT/G-SETUP synthetic positive paths and targeted gate-negative cases; other gates stay in-progress because this pilot has no product evidence that warrants PASS. FW-TASK-020 remains in progress until a real app-hosted attestation is exercised, the remaining required bypass/valid-path matrix is evidenced, and an independent reviewer accepts the complete scope. This pilot does not establish that the framework can build a production-grade application.

## Owner disposition and implementation requirement

**DECISION-019 — trusted CI attestation required (2026-10-21).** The repository owner selected provider-verifiable attestation bound to the exact source revision, required-check manifest, and trusted workflow identity. Local command output may support diagnostics but cannot support G-IMPL PASS. New apps without configured and successfully verified provenance must remain `in-progress` or `blocked`; existing initialized apps are not silently migrated. Revisit when a provider-neutral verifier is available or the configured provider/trust boundary changes. The decision does not claim an attestation proves test quality, branch protection, or production readiness.

The implementation now cryptographically verifies the provider attestation and inspects the signed report for exact repository, signer workflow, protected ref, source SHA, required-check manifest digest, required check IDs, and successful results. Unit tests cover verifier invocation and fail-closed cases; an app-hosted attestation has not yet been observed. Missing verifier, unavailable provider, malformed report, signature/identity mismatch, or stale inputs fail closed in the local validator. App owners must observe and configure branch protection separately; the framework must not infer it from workflow YAML.
